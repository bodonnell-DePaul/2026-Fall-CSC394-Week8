# Preview Demo Checklist - CSC 394

The preview demo is a rehearsal-quality presentation of your project. Show the audience what the application can do, demonstrate its most important user flows, and be ready to explain what is working and what still needs attention.

## Before class

- [ ] The application runs in the environment you plan to use.
- [ ] The main demo flow works from beginning to end without live debugging.
- [ ] Demo data and any test accounts are ready.
- [ ] You have a fallback plan if the deployed version or a live dependency fails.
- [ ] Your slides, links, browser tabs, and demo environment are ready to share.
- [ ] You have rehearsed the presentation and can finish within the time limit announced for class.
- [ ] Every team member knows their speaking part and can explain how their contribution fits into the project.
- [ ] **Every group member has their camera on for the entire presentation - from start to finish, whether they are speaking or not.**

## During the presentation

- [ ] Briefly explain the problem your project addresses and who it is for.
- [ ] Demonstrate the application itself; slides alone are not a substitute for working software.
- [ ] Walk through the primary user workflow clearly, from the user's starting point to the result.
- [ ] Show the important supporting features that make the project feel like a coherent product.
- [ ] Be clear about what is implemented and connected, what is mocked or incomplete, and what remains.
- [ ] Explain the relevant front-end, API, data, and deployment pieces; be ready to discuss testing and reliability.
- [ ] Make sure every team member contributes to the presentation and can speak to the overall system.
- [ ] Keep all group members' cameras on throughout, including while another person is presenting.

## Questions and project status

- [ ] Be prepared to answer questions about how the application works, how it was tested, and what risks remain.
- [ ] Describe remaining work honestly and identify the next steps toward the final demo.
- [ ] If something fails, explain the issue briefly and use your fallback plan rather than spending the presentation debugging.

## Avoid

- [ ] Showing only slides, static screens, or disconnected mockups.
- [ ] Spending the presentation on setup, login problems, or troubleshooting.
- [ ] Claiming unfinished or mocked features are complete.
- [ ] Letting one person present the whole project while the rest of the team is absent from the presentation.
- [ ] Displaying passwords, API keys, database URLs, or other secret values.
- [ ] Turning the preview into a list of features without showing the user experience.

**Final check:** The preview should show a functioning, understandable product and a team prepared to explain it. Be clear about what works, what needs polish, and how you'll address the remaining risks before the final presentation.
